==============================
RAPPORT D'AUDIT COMPLET DU SITE
==============================

1. Résumé général
- État global : Partiellement opérationnel avec plusieurs fonctionnalités coeur OK, mais 2 flux métier critiques KO (facturation création et création dépense) + anomalie CORS dashboard.
- Projet lancé : Oui (avec correction temporaire requise pour ml-service)
- Frontend : Démarre et navigation principale fonctionnelle (home, login, dashboard), mais erreur console bloquante sur appel ML cashflow (CORS).
- Backend : Microservices NestJS + gateway démarrent et répondent correctement sur les endpoints testés.
- Base de données : PostgreSQL opérationnelle, CRUD client validé, cohérence relationnelle partielle (rejets métier sur invoices/expenses).
- Gravité globale : Haute

2. Stack détectée

- IA/ML : FastAPI ml-service (8000), chatbot-finance FastAPI RAG (8001), Ollama (11434)
- DB : PostgreSQL 15 via Docker + Prisma par service
- Infra locale : Docker Compose (postgres, pgadmin, redis)

5. Bugs détectés
- Critique : Echec création dépense (HTTP 500)
  - Symptôme : POST /expenses retourne 500.
  - Preuve log : Prisma invalid input syntax for type uuid: "".
  - Impact : Flux dépenses inutilisable en création.
  - Cause probable : mapping contexte utilisateur/tenant incomplet (UUID vide transmis à Prisma).

- Haute : Echec création facture (HTTP 403)
  - Symptôme : POST /invoices retourne "Business not in this tenant".
  - Impact : Flux principal facturation bloqué dans ce contexte utilisateur.
  - Cause probable : incohérence businessId/tenantId injectés entre JWT, headers et guard tenant.

- Haute : CORS sur dashboard pour cashflow ML
  - Symptôme frontend console : Request header field x-business-id is not allowed by Access-Control-Allow-Headers.
  - Impact : prévision de trésorerie indisponible côté dashboard (fallback simulé).
  - Cause probable : config CORS incomplète côté gateway/ml proxy.

- Moyenne : ml-service non démarrable sans .env local
  - Symptôme : RuntimeError DATABASE_URL must be set in backend/ml-service/.env.
  - Action d’audit : création temporaire backend/ml-service/.env avec DATABASE_URL pour permettre les tests.
  - Impact : bootstrap non autonome sans correctif manuel.

- Moyenne : notifications email admin en erreur 401 (Brevo)
  - Symptôme log : authentication not found in headers (401).
  - Impact : emails externes non envoyés.
  - Cause probable : clé API manquante/incorrecte dans environnement notification-service.

- Faible : traces historiques EADDRINUSE dans logs runtime
  - Symptôme : erreurs anciennes de ports déjà utilisés.
  - Impact actuel : non bloquant après nettoyage des ports.

6. Ce qui marche
- Démarrage global backend/frontend/docker via scripts existants.
- Authentification admin et émission JWT.
- Contrôles d’accès de base (401 sans token, 404 ressources absentes).
- Endpoints admin/roles en lecture.
- CRUD complet client (create/read/update/delete soft).
- Accès chatbot santé et service opérationnel.
- Dashboard accessible après login.

7. Ce qui ne marche pas
- Création de dépense (500).
- Création de facture dans le contexte testé (403 tenant/business mismatch).
- Appel ML cashflow depuis dashboard (CORS, net::ERR_FAILED).
- Bootstrap ML totalement autonome sans fichier .env ml-service.
- Envoi email Brevo admin-registration (401).

8. Non testé
- Upload de fichiers/receipts réel.
- Workflow complet notifications in-app et websocket chat multi-utilisateurs.
- Génération PDF et envoi facture email de bout en bout.
- Flows avancés 2FA (generate/enable/verify) avec OTP réel.
- Tests e2e/unit automatisés par service (non lancés dans ce run d’audit manuel).

9. Recommandations
- Corriger le contexte utilisateur dans expense-service (userId/businessId/tenantId) avant prisma.expense.create.
- Harmoniser la résolution tenant/business dans invoice-service + TenantGuard + gateway headers.
- Ajouter x-business-id à Access-Control-Allow-Headers côté API concernée (gateway/ml) et valider preflight OPTIONS.
- Formaliser backend/ml-service/.env.example et génération automatique dans start-all.sh.
- Corriger les credentials Brevo (API key) et ajouter health check email provider.
- Ajouter un test d’intégration smoke pour POST /invoices et POST /expenses dans CI.
- Ajouter observabilité structurée (logs corrélés request-id) pour diagnostic cross-service.

10. Conclusion
- Le socle applicatif est bien déployable localement et plusieurs briques critiques sont fonctionnelles (auth, admin, roles, clients, UI login/dashboard).
- Deux défauts métiers majeurs empêchent une validation complète production-ready : création facture et création dépense.
- Une anomalie CORS sur le dashboard dégrade les fonctionnalités ML côté front.
- Après correction de ces points, un second audit court de validation finale est recommandé.
